# ТЗ: страница «Заявки» (CRM) в CMS

## 0. Контекст — что уже есть

Таблица `public.leads` в Supabase уже создана и наполняется (миграция [`20260808000000_create_leads.sql`](../supabase/migrations/20260808000000_create_leads.sql)). Каждая отправка формы на сайте (`src/app/api/contact/route.ts`) параллельно шлёт лид в Telegram **и** пишет строку в эту таблицу. Просмотреть эти строки сейчас негде — в `/admin` нет ни одной страницы, которая их читает.

Важный побочный факт: на странице «Аналитика» (`src/app/api/admin/analytics/route.ts:149`) число заявок сейчас **оценочное** (`leadsCount = Math.max(Round(3 * (daysCount/7)), 1)`), не берётся из `leads`. Эта страница ТЗ не чинит аналитику, но после её реализации возникнет соблазн — стоит завести отдельной задачей, не смешивать со Волной этой страницы.

Схема `leads` (готова, не меняем):

| Поле | Тип | Примечание |
|---|---|---|
| `id` | uuid | PK |
| `name` | text | обязательное |
| `phone` | text | обязательное |
| `source` | text | название формы/страницы отправки |
| `comment` | text | текст заявки (проект/сообщение) |
| `contact_method` | text | «Whatsapp» / другое |
| `status` | text | `new` \| `in_progress` \| `contacted` \| `closed` \| `junk` (constraint в БД) |
| `attribution` | jsonb | `{ firstTouch, lastTouch, deviceType, userPath }` — см. `src/lib/utm.ts` |
| `created_at` | timestamptz | сортировка по умолчанию — desc |
| `updated_at` | timestamptz | триггер `set_updated_at` |

RLS уже настроен: `is_cms_admin()` имеет `select/update/delete` — значит серверные экшены могут работать через обычный авторизованный `createClient()` (`@/lib/supabase/server`), как в `src/app/admin/actions.ts`, без сервис-ключа.

## 1. Маршрут и навигация

- Новая страница: `/admin/crm` — серверный компонент `src/app/admin/crm/page.tsx`, по образцу `src/app/admin/analytics/page.tsx`:
  - `getAdminSession()` → редирект на `/admin/login`, если нет сессии;
  - грузит первую страницу заявок на сервере (см. п. 3), передаёт как `initialLeads` в клиентский компонент — без спиннера при первом заходе;
  - `export const dynamic = "force-dynamic"` (данные меняются постоянно).
- Клиентский компонент: `src/components/admin/CrmLeadsClient.tsx` (по образцу `DashboardClient.tsx` / `TrashDashboardClient.tsx`).
- Пункт навигации в `AdminHeader.tsx`: добавить между «Кейсы» и «Корзина» (порядок по частоте использования — заявки смотрят чаще, чем корзину). Иконка `Inbox` из `lucide-react` (уже используется в проекте, есть в зависимостях через lucide-react), подпись «Заявки». Бейдж с количеством новых (`status = 'new'`) рядом с иконкой — по аналогии с тем, как задумывался draft-counter на дашборде (`DashboardClient.tsx` считает `draftCount`) — считаем `newCount` так же на сервере в layout или через lightweight-запрос в самом `AdminHeader`, см. открытый вопрос в п. 7.

## 2. Вёрстка — переиспользуем существующие токены, не изобретаем новые

Простая одна таблица, без карточек, без графиков. Компоненты, которые уже есть в `admin-theme.css` и подходят без изменений:

- Шапка страницы — `.peak-admin__page-header` + `.peak-admin__page-title` («Заявки»), в `page-header-actions` — счётчик `X новых из Y всего` текстом (`.peak-admin__page-meta`), без отдельной статистической плашки (не нужен `.peak-admin__stat-bar` — это не аналитика, это рабочий список).
- Панель фильтра/поиска — `.peak-admin__search` + `.peak-admin__input` (по имени/телефону) и переключатель статуса `.peak-admin__period-switcher` / `.peak-admin__period-btn` (переиспользуем компонент из аналитики один в один — это уже готовый «pill-switcher» на нужную нам механику: «Все / Новые / В работе / Связались / Закрыты / Спам»).
- Таблица — `.peak-admin__case-table` / `.peak-admin__case-table-head` / `.peak-admin__case-table-row` (тот же grid-паттерн, что в `CasesGridEditor.tsx`), колонки свои (см. п. 3). Без drag-n-drop — `dnd-kit` не нужен, заявки не переупорядочиваются.
- Статус-бейдж в таблице — `.peak-admin__badge` с вариантами `--success` (`contacted`/`closed` — зелёный), `--danger` (`junk` — красный), `--neutral` (`in_progress`) и отдельно акцентный для `new` (`peak-admin__hairline-status`, уже даёт зелёный/серый паттерн — для `new` взять акцентный coral, чтобы новые заявки визуально «кричали», это единственное место, где по правилам дизайн-системы (см. `thepeak-cms-redesign.md`, п. 2) акцент **можно** использовать на статусном бейдже — там указано «не использовать coral для бейджей ВИДЕО/ЧЕРНОВИК», но это не отменяет его для сигнала «требует внимания», это разные по смыслу состояния).
- Пустое состояние — `.peak-admin__empty` + `.peak-admin__empty-icon` (иконка `Inbox`), текст «Заявок пока нет» / «По этому фильтру ничего не найдено».
- Уведомления после действий — `.peak-admin__notice--success` / `--error`, как в `DashboardClient.tsx`.
- Радиусы — 0 везде (без исключений, см. `thepeak-cms-redesign.md` п. 2.1). Тени — только `--peak-shadow-sm` на строке при hover, если понадобится, по аналогии с `.peak-admin__case-table-row:hover`.

## 3. Колонки таблицы

| Колонка | Источник | Поведение |
|---|---|---|
| Дата | `created_at` | Формат `дд.мм.гг чч:мм`, часовой пояс `Asia/Qostanay` (как в `lead-notification.ts`, `formatCapturedAt`). Сортировка по умолчанию — новые сверху. |
| Имя | `name` | Просто текст, полужирный. |
| Телефон | `phone` | Кликабельная ссылка `tel:`, рядом иконка WhatsApp-ссылки, если `contact_method === 'Whatsapp'` (используем `whatsappUrl()` из `lead-notification.ts`, либо вынести эту функцию в общий `@/lib/utils`, если понадобится и на сайте, и в CRM — избегаем копипасты). |
| Источник | `source` + `attribution.firstTouch.source` | Основной текст — `source` (какая форма); мелким моно-текстом под ним — `attribution.firstTouch.source` (канал: Google Ads/Meta Ads/органика и т.д.), если `attribution` не пустой объект. |
| Комментарий | `comment` | Обрезка до 1 строки с `text-overflow: ellipsis`, полный текст — по клику разворачивается (`title=` атрибут как минимум, без модалки — это не редактор). |
| Статус | `status` | `<select>` inline (`.peak-admin__select`, компактный) или badge с dropdown-меню — см. открытый вопрос п. 7. Смена статуса — сразу `PATCH`, без отдельной кнопки «Сохранить» (тот же оптимистичный паттерн, что и `toggleStatus` в `DashboardClient.tsx`: меняем локальный state сразу, откатываем при ошибке). |
| Действия | — | Иконка-кнопка «Удалить» (`.peak-admin__icon-button--danger`, `window.confirm` перед удалением — как `removePage` в `DashboardClient.tsx`). |

Строка **не кликабельна целиком** (в отличие от `DashboardClient`/`CasesGridEditor`, где клик по строке ведёт в редактор) — у заявки нет отдельной детальной страницы в этой версии, весь нужный контекст помещается в строку.

## 4. Данные и серверные экшены

Все операции — через `src/app/admin/actions.ts` (расширить существующий файл, не создавать новый) по образцу `togglePageStatusAction`/`deletePageAction`:

```ts
// Новые экшены в actions.ts
async function getLeadsAction(filter: { status?: LeadStatus; search?: string; page: number })
async function updateLeadStatusAction(id: string, status: LeadStatus)
async function deleteLeadAction(id: string)
```

- Чтение — server component на странице делает первый запрос напрямую через Supabase server client (без API route, как это уже принято в `admin/analytics/page.tsx` → `AnalyticsDashboardClient`, который сам фетчит `/api/admin/analytics`). **Решить**: либо серверный `page.tsx` фетчит первую страницу заявок напрямую, а фильтрация/поиск/пагинация на клиенте дергают новый `src/app/api/admin/leads/route.ts` (GET с query-параметрами `status`, `q`, `page`) — этот вариант согласован с уже существующим паттерном `api/admin/cases-list`, предпочтителен.
- `status`-константа: вынести `LeadStatus = 'new' | 'in_progress' | 'contacted' | 'closed' | 'junk'` и русские подписи (`Новая`/`В работе`/`Связались`/`Закрыта`/`Спам`) в `src/types/cms.ts` либо новый `src/types/leads.ts`, чтобы клиент и сервер не расходились со значениями CHECK-constraint в БД.

## 5. Пагинация и объём

Простая версия без бесконечной прокрутки: `limit 30`, кнопка «Показать ещё» (не полноценный пагинатор — соответствует духу «простая страница» из задачи). Фильтр по статусу и поиск сбрасывают пагинацию на первую страницу.

## 6. Что осознанно **не** входит в эту версию

Чтобы страница осталась простой, как попросили:

- Без назначения ответственного (assignee) — заявки ведёт один человек (Яков), поле не нужно.
- Без экспорта в CSV/Excel — если понадобится, отдельная задача.
- Без истории изменений статуса — только текущий `status` + `updated_at`, без лога «кто/когда менял» (в БД для этого нет отдельной таблицы, добавлять — отдельное решение).
- Без интеграции с аналитикой (реальный `leadsCount` вместо оценочного) — см. п. 0, отдельная задача.
- Без bulk-действий (массовое изменение статуса/удаление нескольких сразу).

## 7. Открытые вопросы — нужно решить перед реализацией

1. **Название пункта меню и роут** — «CRM» звучит шире, чем есть по факту (это не сделки/воронка, а список заявок). Предлагаю называть пункт меню «Заявки», роут `/admin/crm` можно оставить как есть или переименовать в `/admin/leads` — не принципиально, но роут и подпись лучше не расходиться по смыслу.
2. **Статус меняется через `<select>` или через popover с бейджами?** `<select>` — быстрее в реализации и уже есть готовый класс `.peak-admin__select`; popover с цветными бейджами выглядит презентабельнее, но это дополнительный компонент, которого пока нет в системе.
3. **Счётчик новых заявок в шапке** (`AdminHeader.tsx`) — топбар сейчас серверных данных не получает вообще (чистый client component на `usePathname`). Добавление счётчика потребует либо параллельного клиентского fetch с поллингом, либо переноса топбара на server component с пробросом count через layout. Для «простой страницы» можно на первой итерации не делать live-счётчик в топбаре и обойтись счётчиком только на самой странице `/admin/crm` — дешевле и не меняет архитектуру `AdminHeader`.
